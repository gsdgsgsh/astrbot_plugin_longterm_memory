## 📦 安装与使用

1. 将插件文件夹放入 AstrBot 数据目录下的 `data/plugins/`（文件夹名必须是 `astrbot_plugin_longterm_memory`）
2. 重启 AstrBot，或到 Dashboard → 插件页热重载
3. 插件自动开始工作；管理页在 Dashboard → 插件 → 长期记忆
4. 检查启动日志确认 Embedding / LLM / Rerank Provider 已就绪

**依赖**：必选依赖见 `requirements.txt`（仅 `numpy`）。可选依赖（ChromaDB 向量后端）见 `requirements-optional.txt`。

**版本要求**：AstrBot >= 4.26.0（管理界面使用官方 Plugin Pages + `register_web_api`，该机制自 4.26 起提供）。低版本下插件主体功能（对话记忆）仍可用，仅管理页面不可见。

## 🎯 核心功能

- **对话总结**：LLM 定期自动总结对话，压缩为精炼记忆。支持轮数/时间/信息密度/时间跨度四种智能触发
- **向量检索**：基于语义相似度召回最相关历史记忆，注入对话上下文。支持 NumPy（默认）和 ChromaDB（可选）两种后端
- **上下文窗口感知**：自动检测模型上下文窗口，短对话跳过记忆检索避免不必要延迟
- **Embedding 缓存**：LRU 缓存同义查询结果，减少重复 API 调用
- **记忆衰减 + 重要性加权**：越久远记忆权重越低，重要记忆优先召回
- **记忆冲突检测**：新总结与已有记忆高度相似时自动判断是否合并更新
- **叙事时间追踪**：LLM 总结时提取角色扮演中的叙事时间线
- **人设漂移检测**：LLM 自动检测角色状态变化（身份/年龄/职业等），用户二次确认后更新人设
- **用户画像**：自动提取用户特征、偏好、习惯，按间隔增量更新
- **好感度系统**：追踪用户对机器人的态度变化（LLM 评估 + 规则引擎 + EMA 平滑）
- **Dashboard 插件页面**：管理界面并入 AstrBot Dashboard（总览/记忆/画像/好感度/配置），免独立端口与自建登录

### 历史上已移除的功能

随机事件、AI 日记、记忆标签分类、多机器人覆盖、分段回复已移除以精简臃肿功能。

## 🌐 管理界面（AstrBot Dashboard 插件页面）

**访问方式**：AstrBot Dashboard → 插件 → 长期记忆 → 打开「记忆管理」页面。

页面以受限 iframe 形式嵌入 Dashboard，**登录鉴权完全由 Dashboard 负责**，因此本插件不再需要独立端口、访问令牌或 TOTP 两步验证。

**管理功能**：
- 📊 总览（统计卡片 / 近 14 天记忆增长折线 / 各作用域记忆量 / **嵌入诊断** / **一键重新嵌入全部**）
- 📝 记忆管理（**内容搜索**、类型筛选、**仅看嵌入失败**、单条重新嵌入、**批量补嵌**、**批量删除失败项**、**待总结缓冲区查看**）
- 👤 用户画像（查看 / 编辑 / 清除）
- ❤️ 好感度（分数、等级、趋势图、近期变化）
- ⚙️ 配置（可视化编辑并保存）

**旧数据调整**：
- **画像残缺** → 「画像」页点 **🔄 从记忆重建**：旧版在保存时就截断了画像，但画像由记忆推导而来，可重新生成完整版本
- **记忆结构乱**（不同话题混一条 / 同话题拆两条）→ 「记忆」页点 **🧩 重整记忆**：LLM 合并同话题碎片、拆分混合话题；**重整前自动备份**，不满意可点 **↩ 回滚重整**
- **单条不对** → 每条记忆的 **✏️ 编辑**：直接改文本与重要性，保存后自动重新生成向量
- **想换隔离模式** → 记忆页点 **📤 迁移到…**：把当前作用域的记忆整体**迁移/复制**到另一个作用域（如 `user` → 某个 `conversation`）。注意记忆条目**不记录来源对话**，所以只能整体搬，无法自动还原到"原来那个对话"；重复内容自动跳过，迁移前自动备份
- ⚠️ 无法"重新总结原始对话"：缓冲区在总结后即清空，旧数据的原始对话已不在插件内

**提示词模板改过怎么办？**
「配置」页现在可以直接**查看 / 编辑**三个提示词模板（多行文本框），并显示「当前 N 字符 · 默认 N 字符」。

- 自动迁移**只替换仍带旧版特征串的模板**——你手动改过的**不会被覆盖**（刻意设计）。
- 想改用插件自带的新版：找到该项点 **↺ 恢复默认** → 保存。
- 三项中**只有亲密度评估提示词的约束不会被插件自动追加**，其余两项的关键规则由插件在调用时自动拼接，自定义模板影响较小。

**升级后想套用新默认值？**
**插件启动时会自动完成**：只把"当前值恰好等于旧默认值"的项（说明你从没改过）升级为新默认，你手动改过的一律不动，并写入日志（配置项已升级：key 旧值 → 新值）。
若想手动改某一项，到「配置」页点字段旁的 **↺** 填回默认值（改完点「保存配置」）。

> ⚠️ **不要用 AstrBot 插件页的"整体恢复默认"**：它会把 profile_enabled / affection_enabled /
> persona_drift_enabled 一并重置为 **false**（这三个默认都是关的），等于**静默关闭用户画像与亲密度系统**；
> chromadb_enabled / enable_rerank / keep_raw_messages 也会被关掉，embedding_provider_id 等 Provider 指定项会被清空。

**嵌入失败了怎么办？**
1. 「总览 → 嵌入诊断」先点 **测试嵌入连通性** —— 确认 Embedding Provider 是否可用（会显示向量维度与耗时，失败时显示具体原因）
2. Provider 正常 → 点 **一键重新嵌入全部**，右下角进度条显示补嵌进度（分批调用，不阻塞页面）
3. Provider 不可用 → 到「配置」页确认 `embedding_provider_id`，或检查 AstrBot 的嵌入模型配置
4. 实在无法嵌入的，可用「删除失败项」清理（这些记忆本来就不参与语义检索）

### ❤️ 亲密度（原「好感度」）

分数衡量的是**用户与助手的关系有多近**，而不是"用户有多捧助手"。评分取向：

| 信号 | 权重 | 说明 |
|---|---|---|
| **自我表露** | 高 (+0.25) | 分享自己的经历、感受、计划、困扰 —— 信任的表现 |
| **关系连续性** | 最高 (+0.4) | 引用共同历史（"上次你说的""还记得"） |
| **深度投入** | 低 (+0.1) | 有实质内容的长消息；**短消息不扣分** |
| 礼貌与暖意 | 很低 (+0.15~0.5) | 谢谢、夸奖、哈哈哈、喜欢你 —— 只是社交润滑 |
| 明确敌意 | −0.5~−1.0 | 仅限辱骂、"别烦我""受够了"这类 |

**设计原则**：礼貌用语权重刻意压低，且同一加分理由连续出现时**收益对折衰减**（×0.5 → ×0.25），所以"靠刷夸奖涨分"走不通；反过来，**回复简短、提出不同意见、指出助手答错都不扣分**——不需要为了涨分去讨好 AI。

#### 分数偏低？让 AI 重新评估

分数是在**旧规则**（增益系数 0.15、每日上限 10）下累积的，升级后普遍偏低。亲密度页点 **🤖 让 AI 重新评估**：

AI 会读取你的**实际互动记录**——累计次数与正负比例、最近 20 条变化记录、最多 25 条记忆摘要——按下面的准则重新判定：

- 依据**实际互动内容**：交流是否长期、深入、稳定；是否分享生活与感受；是否引用共同经历
- **礼貌用语（谢谢、夸奖）不能作为高亲密度的依据**
- 互动多但内容浅 → 「熟人」而非「朋友」；互动很少 → 不给高分

结果与理由直接落库（历史里标记为「AI 重新评估：…」）。这属于**修正**，不受每日上限限制。

> 面板里还提供一个**统计参考值**（按互动量用当前参数粗算），仅供对照；手动设定分数也保留了。

## 🧯 常见问题

### ChromaDB 装了却提示"未安装/回退到 NumPy"

1. **`chromadb` 不在 `requirements.txt` 里**——它是可选依赖，放在 `requirements-optional.txt`，AstrBot **不会自动安装**。这是刻意设计，避免给不想用 ChromaDB 的用户强装一堆依赖
2. **必须装进 AstrBot 运行所用的那个 Python 环境**。装了但没生效，绝大多数是"pip 装到了另一个解释器"：
   ```bash
   # 先确认 AstrBot 用的是哪个解释器
   docker exec -it <容器名> python -c "import sys; print(sys.executable)"
   # 用它来安装
   docker exec -it <容器名> /path/to/python -m pip install chromadb
   ```
3. **Docker 部署注意**：容器内 `pip install` 在**容器重建/升级后会丢失**。要长期生效，请写进自定义 Dockerfile，或在 `docker-compose` 里挂载持久化的虚拟环境
4. **启用后必做一步**：到「总览 → 嵌入诊断」点 **🔄 回填向量到 ChromaDB**。
   插件只在**新增记忆**时写向量；切换后端前已有的记忆不在集合里，而检索时 Chroma 一旦返回结果就不会回退 NumPy，表现为"旧记忆查不到"
5. **怎么看真实原因**：「总览 → 嵌入诊断」会显示 ChromaDB 的三种状态——**可用 / 未安装 / 已安装但导入失败**，并附上**当前解释器路径**与**导入错误原文**。若显示"已安装但导入失败"，通常是缺少传递依赖或版本冲突，按错误原文处理即可

### 改了 metadata.yaml 的 author / name 之后，记忆全没了？

AstrBot 的插件 KV **按 plugin_id 分命名空间**，而（源码 star.py）：

```python
plugin_id = f"{(author or 'unknown').lower()}/{(name or 'unknown').lower()}"
```

所以只要改 `author` 或 `name`，插件就会去读一个**全新的空命名空间**——**数据一条没丢，只是"看不见"**。

- 本插件启动时会**自动把旧命名空间的数据补搬过来**（只补缺失的键，不覆盖现有数据），日志会打印「检测到旧 KV 命名空间…已补搬 N 项」
- 手动兜底：把 `author` 改回原值 → 重载（数据回来）→ 「💾 导出备份」→ 改回新值 → 重载 → 「📥 导入备份」
- 启动日志现在会打印当前 **KV 命名空间**，可用它核对

### 升级/重装插件后记忆全没了

**AstrBot 卸载插件时会清空该插件的全部 KV 数据**（源码 `star_manager.py` → `sp.clear_async("plugin", plugin_id)`，日志会打印 `Cleared KV data for plugin ...`），而本插件的记忆就存在 KV 里。

因此：

- **升级请用 Dashboard 的「重载」**，不要"卸载后重新上传"
- 卸载时**不要勾选「同时删除数据」**
- 「卸载加载失败的插件」同样会清理 KV——插件加载失败时**先修好再重载**，不要急着卸载
- **最稳妥**：定期到「总览 → 💾 数据备份」导出 JSON。文件存在你自己的电脑上，卸载/重装/换机器都不会丢

### 怎么确认是不是被卸载清掉的

```bash
docker logs <容器名> 2>&1 | grep -iE "Cleared KV data|Deleted persistent data"
```

有输出就说明是该插件的 KV 被清理了。此时可检查 `data/shared_preferences.json` 里是否还留有该插件的数据。
### 管理页只有 1 个作用域

`memory_scope = user` 时，**一个用户只有一个作用域**（该用户所有对话共用）。这符合预期，不是数据丢失。需要"每个对话独立"请改成 `conversation`（可用记忆页的「📤 迁移到…」把旧记忆搬过去）。
